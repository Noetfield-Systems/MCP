# MCP Foundry OAuth — GitHub private GET connection

OAuth has two distinct uses:

1. **Upstream API connection (implemented):** a Foundry workspace owner authorizes Foundry to call `api.github.com` through a private MCP server. GitHub app credentials are configured by the operator.
2. **Client-to-Foundry OAuth Authorization Server (not implemented here):** a separately registered user/client would sign in to Foundry via the MCP authorization specification. The existing private MCP endpoint currently uses a personal bearer API key.

Do not market the first as the second.

## Current implementation

- Authorization-code flow with state bound to the signed-in Foundry account, single-use hashed state and **PKCE S256** challenge/verifier.
- A fixed GitHub authorization and token endpoint. The browser cannot supply a custom authorization domain or token URL.
- Token exchange occurs only on the Foundry backend, with no credentials in frontend state or GitHub source.
- OAuth access/refresh tokens and PKCE verifier stored with **AES-256-GCM** authenticated encryption and an owner-bound additional authenticated data value.
- Per-account token storage; refresh on expiration when GitHub has returned a refresh token; local revocation removes tokens and disables all bound server endpoints.
- Owner chooses which private Foundry MCP server can use GitHub OAuth. Binding moves a server to Private + Draft; public publish attempts with an OAuth binding are explicitly rejected.
- Credential forwarding is limited to `api.github.com` with the same DNS-pinned, public-IP-only, redirect-disabled, bounded GET transport used by anonymous tools.
- Existing public read-only GET servers are unchanged. This does not enable arbitrary `POST` or third-party OAuth scopes.

## Required provider registration (real dependency)

Create a dedicated **GitHub OAuth App for MCP Foundry** in a GitHub organization or account that can legitimately operate it. Do **not** use GitHub connector personal tokens or another portfolio product's OAuth app. Set the application authorization callback URL to the exact public service URL:

`https://mcp-foundry-web-production.up.railway.app/api/oauth/github/callback`

Configure the following as private Railway variables on the MCP Foundry service:

- `GITHUB_OAUTH_CLIENT_ID` — application ID
- `GITHUB_OAUTH_CLIENT_SECRET` — provider app secret
- `FOUNDRY_OAUTH_ENCRYPTION_KEY` — 32 securely generated bytes represented as 64 hex characters
- `PUBLIC_URL` — canonical HTTPS origin (already configured)

The encryption key must be generated and held outside Git history. Once these are configured, visit `/oauth` and authorize GitHub. The requested initial OAuth scope is `read:user`, which is not an enterprise repository authorization system. An account can then bind a compatible `api.github.com` tool server, test privately, and republish with Private visibility.

**Live connection state cannot be marked verified unless an actual consenting owner completes the GitHub callback, the encrypted credential is stored and a private MCP client invocation reaches the GitHub API with a valid token.**

## Security and provider notes

GitHub app authorization is provider-dependent. The authorization URL requests PKCE; the code-verifier is redeemed at GitHub's token endpoint. Refresh handling depends on whether the actual GitHub app issued an expiring access token. OAuth state expires after 10 minutes. Revoking in Foundry deletes local credentials and unpublishes bound endpoints; revoke the OAuth grant in GitHub account settings to invalidate any outstanding remote token.

Owner personal API keys still authenticate to Foundry's private MCP endpoint. This is deliberately separate from your GitHub authorization.
