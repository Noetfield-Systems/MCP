این سند بازنویسی کامل متن «100 Upgrades & Growth Plan v2» است: تز محصول حفظ شده، پیشنهادها به چالش کشیده شده‌اند و ۱۰۰ اقدام با ترتیب جدید، خروجی قابل سنجش و نگاشت به نسخهٔ قبلی آمده‌اند. این سند پیشنهاد اجرایی است؛ انتشار کد، فعال‌سازی پرداخت، جذب مشتری یا وصول پول را گزارش نمی‌کند.

## ۱. تصمیم پیشنهادی

Foundry باید سریع‌ترین مسیر عملی برای رساندن API صاحب کسب‌وکار به استفادهٔ واقعی در کلاینت‌های AI باشد: انتخاب ابزار مناسب، ساخت، تست، اتصال، انتشار و نگهداری. «سریع‌ترین» هدف رقابتی ماست و تا اندازه‌گیری مقایسه‌ای، ادعای اثبات‌شدهٔ تبلیغاتی نیست.

**وعدهٔ قابل فروش:** API موجودت را به یک تجربهٔ قابل استفاده در AI تبدیل می‌کنیم؛ با endpoint، ابزارهای منتخب، اتصال آزموده‌شده و مسیر تحویل روشن.

سه موتور مکمل:

1. **درآمد امروز:** اجرای بسته‌های مشخص برای صاحبان API و مشتریان آژانس‌ها، با دریافت وجه و تحویل واقعی.
2. **رشد محصول:** ساخت از داخل AI، Studio ساده، قالب قابل تکثیر و نصب از صفحهٔ مستندات مشتری.
3. **درآمد تکرارشونده:** میزبانی، سازگاری کلاینت، مراقبت از تغییرات API و پشتیبانی محدود و مشخص.

بازار هدف اصلی، صاحب API با کاربر یا مشتری موجود است. توسعه‌دهندهٔ علاقه‌مند کانال ورود و کاربر محصول است؛ لزوماً خریدار خدمات نیست. آژانس می‌تواند هم خریدار چند پروژه و هم کانال توزیع باشد. پروژه‌های Web3 و دادهٔ آن‌چین مسیر تخصصی معتبر همین محصول می‌مانند.

دو جزئیات کد برای اولویت‌گذاری اهمیت دارند: ابزار `publish_server` وجود دست‌کم یک tool را کنترل می‌کند، اما این به‌تنهایی اثبات موفقیت یک سناریوی کاربر نیست. همچنین ثبت `tool_events` در مسیر اجرای مدیریت‌شده خطای ذخیره‌سازی را با `catch` نادیده می‌گیرد؛ در نتیجه تکیه بر این جدول برای صورتحساب مصرفی یا ادعای شمارش کامل اجراها زود است. اجرای محصول ادامه دارد؛ پیش از قیمت‌گذاری مصرفی، شمارش باید قابل اتکا شود.

## ۵. دوازده پیشنهاد طلایی، به ترتیب اولویت

### ۱) بستهٔ «API Agent Launch» بفروشیم

تحویل شامل یک API، مجموعهٔ کوچک ابزارهای مفید، دو سناریوی واقعی، endpoint، اتصال به یک کلاینت مشخص، صفحهٔ نصب و راهنمای مالکیت است. مشتری خروجی قابل استفاده می‌خرد. دامنهٔ عمومی با محصول فعلی قابل شروع است؛ auth خصوصی یا عملیات نوشتن جدا قیمت‌گذاری می‌شود.

**آزمون:** سه پیشنهاد مشخص به خریداران مناسب؛ سنجش پرداخت، ساعت تحویل و استفادهٔ پس از تحویل. پیشنهاد فروش را می‌توان از روز اول آماده کرد؛ ارسال بیرونی نیازمند دستور ارسال است.

### ۲) «از داخل AI بساز» را محور تجربه کنیم

Foundry خودش MCP Builder است. روی همین قابلیت موجود یک دستور نمونه، جریان قابل ادامه‌دادن، preview ابزارها و اتصال آزموده‌شده بسازیم. ساخت از داخل کلاینت و Studio باید از یک منطق backend استفاده کنند.

**آزمون:** توسعه‌دهندهٔ مستقل پس از اتصال حساب، یک API پشتیبانی‌شده را در همان محیط import/test/publish کند. هدف اولیهٔ کمتر از ۱۰ دقیقه صرفاً هدف آزمون است، نه وعدهٔ فعلی سایت.

### ۳) دکمهٔ نصب در مستندات مشتری، موتور توزیع باشد

هر پروژهٔ تحویلی یک snippet اختیاری برای «Use with AI» می‌گیرد. بازدیدکنندهٔ مستندات مشتری به صفحهٔ نصب همان API می‌رسد و کلاینت خود را انتخاب می‌کند. endpoint یا credential خصوصی داخل لینک عمومی قرار نمی‌گیرد.

**آزمون:** اولین نصب و اولین فراخوانی از این مسیر ثبت شود. رتبهٔ SEO، پیشنهادشدن توسط مدل یا کاربر خودکار تضمین نمی‌شود.

### ۴) آژانس را خریدار تکرارشونده ببینیم

آژانس دارای چند مشتری API می‌تواند چند تحویل خریداری کند. ابتدا نمونه، scope ثابت و تحویل قابل تکرار؛ بعد workspace چندمشتری، white-label و تخفیف حجمی. قرارداد با آژانس پیش‌شرط فروش مستقیم نیست.

**آزمون:** یک آژانس دو پروژهٔ واقعی بیاورد؛ ثبت‌نام برای عنوان «partner» موفقیت محسوب نشود.

### ۵) APIهای خصوصی را با یک مسیر محدود باز کنیم

اول کلید upstream متعلق به مشتری، روی host مشخص و endpoint خصوصی؛ سپس OAuth همان provider در صورت نیاز. احراز هویت کلاینت به Foundry و مجوز Foundry به API دو مسئلهٔ جدا هستند.

**آزمون:** یک درخواست پولی واقعی با یک روش auth و یک کلاینت مشخص حل شود. لازم نیست ابتدا یک OAuth broker عمومی ساخته شود.

### ۶) ویرایش، endpoint فعال مشتری را قطع نکند

پیشنهاد: `draft_revision` و `published_revision` جدا باشند. تغییر ابزار فقط draft را تغییر دهد؛ publish نسخهٔ تأییدشده را اتمیک جایگزین کند. این کار از مشکلات تحویل و پشتیبانی جلوگیری می‌کند.

**آزمون:** مشتری نسخهٔ A را استفاده کند، سازنده نسخهٔ B را ویرایش کند، A تا انتشار B همچنان پاسخ بدهد؛ rollback هم روشن باشد.

### ۷) ابزار «تشخیص اتصال» عمومی‌تر از کمپین Smithery بسازیم

ورودی: endpoint یا تنظیمات redacted. خروجی: transport، مجوز، ابزارهای قابل کشف، محل شکست و اقدام بعدی. مهاجرت Smithery یکی از کاربردهای آن است. اگر URL رسمی مسئله را حل می‌کند همان را نشان دهیم؛ خدمات برای میزبانی سفارشی و مسائل پیچیده‌تر فروخته شود.

**آزمون:** پنج مورد واقعی را تشخیص دهد و حداقل یکی به تعمیر مفید یا سفارش مرتبط برسد. پیکربندی حاوی token خام ذخیره نشود.

### ۸) سرویس ماهانه را حول تغییر API بفروشیم

نگهداری، یعنی تشخیص تغییر spec، آزمون قرارداد، هشدار خرابی، وصلهٔ محدود و rollback؛ تنها داشتن یک سرور روشن ارزش کافی ایجاد نمی‌کند. مشتری از ابتدا می‌تواند این گزینه را انتخاب کند؛ عرضهٔ آن نیازمند ظرفیت مشخص تحویل است، نه انتظار برای تعداد دلخواه کاربر.

**آزمون:** یک مشتری به‌خاطر این خدمات تمدید کند و زمان پشتیبانی از سقف بسته عبور نکند.

### ۹) ابزارهای کم و دقیق، به‌جای export کور همهٔ endpointها

برای یک سناریو مثل «وضعیت انتشار این مخزن چیست؟» یا «مشخصات این جفت معاملاتی چیست؟» ابزارهای لازم انتخاب، توضیح و آزموده شوند. مدل لازم نیست صدها schema نامرتبط ببیند.

**آزمون:** روی یک مجموعهٔ ثابت درخواست، انتخاب ابزار و پاسخ قابل قبول با نسخهٔ خام مقایسه شود. call بیشتر نشانهٔ بهتر بودن نیست.

### ۱۰) خروجی قابل انتقال و دامنهٔ مشتری، بخشی از ارزش فروش باشد

manifest، schema، نمونه‌های تست و دستور deployment از یک تعریف واحد صادر شوند. دامنهٔ مشتری امکان جابه‌جایی میزبان را آسان می‌کند. «قابل انتقال» را فقط وقتی بگوییم که خروجی خارج Foundry اجرا شده باشد.

### ۱۱) تقاضا را پیش از ساخت بازار ثبت کنیم

request board ساده: API مورد نیاز، کاری که باید انجام شود، بودجه یا مدل خرید و کلاینت مقصد. اولین سفارش می‌تواند دستی به یک سازنده تخصیص یابد. سیستم امتیاز، escrow و payout پیچیده برای این شروع لازم نیست.

### ۱۲) هر سفارش باید یک دارایی قابل تکرار بسازد

بعد از تحویل، اجزای عمومی و مجاز آن به template، آزمون قرارداد، راهنمای نصب و نمونهٔ فروش تبدیل شوند. اطلاعات و کد اختصاصی مشتری بدون مجوز منتشر نشود. هدف، کاهش ساعت تحویل سفارش بعدی است؛ صرفاً تعداد پروژه‌ها را بالا نبریم.

**قاعدهٔ اقتصادی:** Quickstart یک خدمات کوتاه و استاندارد است. اگر تحویل به چند ساعت کار اختصاصی تبدیل شد، سفارش بعدی باید scope یا قیمت متفاوت بگیرد؛ تعهد سفارش پذیرفته‌شده یک‌طرفه تغییر نکند.

مثال صرفاً برای تصمیم داخلی: با نرخ فرصت نیروی کار CA$75 در ساعت و CA$15 هزینهٔ مستقیم فرضی، قیمت ۱۹۹ برای یک ساعت کار CA$109 حاشیهٔ مشارکت و برای سه ساعت کار منفی CA$41 می‌سازد؛ پیش از کارمزد واقعی، مالیات و سربار. در قیمت ۷۹۹، چهار ساعت کار و CA$40 هزینهٔ مستقیم فرضی CA$459 باقی می‌گذارد. این اعداد هزینهٔ واقعی Foundry نیستند؛ باید با زمان و هزینهٔ سفارش‌ها جایگزین شوند.

درآمد وصول‌شده، درآمد شناسایی‌شده، وجه برگشتی، مالیات وصولی و سود یکی نیستند. برای تصمیم تجاری فعلی یک جدول سادهٔ سفارش‌ها کافی است؛ داشبورد مالی جدید لازم نیست.

## ۹. برنامهٔ ۳۰روزه با فروش همزمان

| روزهای ۱۵–۲۱ | export، تشخیص تغییر API و صفحات نصب تکرارشونده | بازگشت مشتری، درخواست معرفی و یک همکاری آژانس | کدام کانال به استفاده و پول می‌رسد؟ |

هدف‌های آزمایشی ۳۰روزه: ۲۰ تا ۴۰ نامزد دقیق، ۸ گفت‌وگوی مرتبط، ۴ پیشنهاد مشخص، ۲ تا ۴ پروژهٔ پولی پذیرفته‌شده، ۱۰ توسعه‌دهندهٔ مستقل فعال‌شده و ۴ سازمان/مالک بازگشتی. این اعداد پیش‌بینی یا نتیجهٔ واقعی نیستند. ظرفیت تحویل اولویت دارد؛ کمپین بزرگ‌تر بدون ظرفیت پشتیبانی مفید نیست.

مثال سناریوی فروش، صرفاً برای مقایسه: دو Launch به ۷۹۹ و دو Quickstart به ۱۹۹ جمعاً CA$1,996 دریافتی ناخالص فرضی می‌سازند؛ سه Quickstart فقط CA$597. اختلاف، دلیل بررسی ارزش سفارش است؛ درآمد خالص و سود از آن قابل استنتاج نیست.

## ۱۰. معیارهای سنجش و قواعد تصمیم

دو شاخص اصلی کنار هم باشند:

1. **استفادهٔ بازگشتی مشتری:** تعداد سازمان‌ها/مالکان خارجی که در هفته استفادهٔ معنادار از endpoint خود دارند. پروکسی اولیهٔ عملی: حداقل سه اجرای موفق غیرآزمایشی در دو روز متفاوت؛ نتیجهٔ واقعی کار با fixture یا بازخورد مشتری سنجیده شود. این threshold قراردادی است و استفادهٔ کم‌تکرار اما ارزشمند جدا گزارش می‌شود.
2. **حاشیهٔ مشارکت تحویل:** درآمد پس از برگشت وجه و حذف مالیات وصولی، منهای کارمزد، هزینهٔ مستقیم زیرساخت/API و زمان تحویل/پشتیبانی با نرخ داخلی معلوم. این با سود خالص شرکت فرق دارد.

| پرسش | سنجهٔ ساده | تصمیم |
|---|---|---|
| آیا پیشنهاد خریدار دارد؟ | پاسخ مرتبط → brief → quote → پرداخت | بدون پاسخ به ۲۰ تماس دقیق، پیام/مخاطب/کانال را اصلاح کنیم؛ ابتدا feature اضافه نکنیم |
| چرا خرید اتفاق نمی‌افتد؟ | علت رد پنج پیشنهاد مشخص | اگر مشکل auth است آن را جلو بیاوریم؛ اگر نیاز نیست محصول بیشتری نسازیم |
| آیا محصول قابل استفاده است؟ | درصد رسیدن به اتصال و اولین اجرای موفق | روی پرتکرارترین محل شکست کار کنیم |
| آیا نتیجه تکرار می‌شود؟ | بازگشت در هفتهٔ بعد و کار واقعی انجام‌شده | workflow و onboarding بر اساس استفاده اصلاح شود |
| آیا خدمات مقیاس می‌گیرد؟ | ساعت تحویل اول و بعدی، سهم اجزای reusable | اگر هر سفارش کاملاً سفارشی شد scope و بسته‌بندی را تغییر دهیم |
| آیا Care می‌ارزد؟ | تمدید و زمان پشتیبانی هر حساب | محدوده یا قیمت با هزینهٔ واقعی هماهنگ شود |
| آیا مهاجرت Smithery ارزش ادامه دارد؟ | پاسخ مرتبط و تعمیر/سفارش طی یک آزمایش کوتاه | اگر فقط تعویض URL بود، راهنمای رایگان بماند و بودجه به offer اصلی برگردد |
| آیا Marketplace زمان مناسبی دارد؟ | درخواست دارای خریدار و عرضه‌کنندهٔ قابل تحویل | یک تراکنش واقعی را دستی انجام دهیم؛ سپس پرتکرارترین بخش را خودکار کنیم |

دادهٔ کم، حکم قطعی دربارهٔ کل بازار نمی‌دهد. این قواعد برای تخصیص وقت هستند. آزمایش فروش پس از اصلاح پیام یا کانال می‌تواند دوباره اجرا شود.

هدف مدیریت کار: حداکثر سه خروجی فعال؛ یک بهبود اتصال، یک خروجی فروش/تحویل، یک دارایی توزیع. حدود ۵۰٪ تلاش برای فروش و تحویل، ۳۰٪ رفع اصطکاک واقعی و ۲۰٪ دارایی قابل تکرار، یک تخصیص آزمایشی مناسب است؛ با حجم سفارش تغییر می‌کند.

## ۱۱. سه جریان رشد و یک حلقهٔ یادگیری

**توزیع از API مشتری:** تحویل integration → صفحهٔ نصب در docs مشتری → استفادهٔ کاربران او → شواهد کاربرد → نصب و APIهای بیشتر. مزیت این مسیر دسترسی به تقاضای موجود است؛ به رتبهٔ بالای موتور جست‌وجو وابسته نیست.

**توزیع از آژانس:** یک پروژهٔ استاندارد → تحویل قابل تکرار → مشتری دوم همان آژانس → سفارش چندتایی → کاهش هزینهٔ فروش و اجرا.

**رشد self-serve:** یک نمونهٔ واقعی → ساخت داخل AI یا Studio → اولین اتصال → اشتراک template/صفحهٔ نصب → سازندهٔ بعدی. پاداش ارجاع تابع استفادهٔ واقعی و ظرفیت هزینه است.

**یادگیری محصول:** درخواست ناموفق یا کار ناقص → تشخیص علت → اصلاح کوچک → آزمون همان سناریو → کاهش شکست در نسخهٔ بعد. منابع این حلقه در خود Foundry باقی می‌مانند؛ لازم نیست سیستم داخلی دیگری ساخته شود.

## ۱۲. طرح فنی پیشنهادی برای اجرای همین ریپو

ساختار فعلی Node/Express/PostgreSQL/MCP SDK حفظ شود. بازنویسی framework یا ساخت یک control plane تازه توجیهی در این بررسی ندارد. اجزای زیر پیشنهاد منطقی‌اند، نه ادعای وجود جدول یا فایل فعلی:

| جزء پیشنهادی | کاربرد | حداقل تغییر |
|---|---|---|
| تعریف نسخه‌دار integration | یک منبع برای Studio، native MCP، export و تست | server، revision، tool definitions و client profile |
| draft و published revision | جلوگیری از قطعی حین ویرایش | pointer فعال با تعویض اتمیک؛ نگه‌داشتن یک نسخهٔ قبلی |
| install receipt | تشخیص setup موفق و منبع توزیع | server/revision، نوع آزمون، host آزمایش‌شده و زمان |
| call event دقیق | سنجش استفاده؛ مبنای آیندهٔ meter | request ID، test/live، نتیجه، error class؛ دادهٔ خصوصی حداقلی |
| شناسهٔ سفارش و مرجع پرداخت | اتصال وصول وجه به کار تحویلی | paid/fulfilled/refunded جدا؛ callback قابل تکرار |
| care check | تشخیص خرابی و تغییر API | job محدود و dedup؛ webhook در صورت وجود منبع، بررسی زمان‌بندی‌شدهٔ کم‌هزینه در غیر آن |

آزمون SDK، سازگاری protocol را بررسی می‌کند؛ برای عبارت «در کلاینت X کار می‌کند»، تست در خود host و جریان auth آن لازم است. نسخه و تاریخ آزمون ثبت شود. سرور ناشناس با requestهای موفق لزوماً کاربران انسانی متمایز ندارد. برای endpoint عمومی، معیارهای anonymous و مشتری احرازشده جدا بمانند.

برای quota، شمارش سپس اجرا در درخواست‌های همزمان می‌تواند سقف را رد کند؛ اگر انتظار سقف سخت وجود دارد، کنترل اتمیک لازم است. این مسئله برای هزینه و طرح مصرفی اهمیت دارد؛ شرط توقف فروش Quickstart عمومی نیست.

| پایگاه شواهد اجرای ابزار | داده به‌تنهایی مزیت دفاع‌پذیر نسازد | از آن برای کاهش پشتیبانی و افزایش موفقیت استفاده کنیم؛ ارزش را بسنجیم |

مزیت دفاع‌پذیر احتمالی مجموعه‌ای از templateهای مسئله‌محور، کیفیت تحویل، نصب در کانال‌های مشتری، تجربهٔ سازگاری و هزینهٔ کمتر نگهداری است. هیچ‌کدام فعلاً moat اثبات‌شده نیستند.
